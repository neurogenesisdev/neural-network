# 2026-08-23 — Grounding a chapter surfaced an ADR; a convention came from a hole in the draft

Third round of the same day. The first
([[20260823-build-spec-schema|log]]) settled the schema, the second
([[20260823-spec-boot-promotion|log]]) promoted `spec/boot`; this one wrote
[[../spec/disk|spec/disk]] — the first chapter with no worked examples behind
most of it — and produced
[[../decisions/20260823-continuous-trim-both-layers|ADR-0014]] on the way, plus
a fourth convention in [[../spec/_schema|_schema.md]].

This is what did not fit in any of them.

## The ADR was not planned, and the mechanism that found it is the point

`spec/disk` needed an assertion about the LUKS container's format parameters.
That is a small question — which fields does `luksFormat` fix, and which change
later? — and answering it meant reading `state/storage.md`'s `## luks` against
what the step was about to write. The PRD says one thing there and the machine
says another, and the two had never been put side by side.

**Nothing about that comparison required cleverness. It required needing an
assertion.** The PRD has been the primary input to three rounds of work. §1.2 was
read in all of them and its discard paragraph is not subtle. What none of those
readings forced was the question *what would a postcondition here have to be true
of*, and that question cannot be answered without resolving the document against
the collector. Prose describing a configuration and prose describing the same
configuration differently can sit in one vault indefinitely; a check that must
pass on the running machine cannot.

The same thing happened one step later and from the other direction.
`btrfs-subvol-mount`'s postcondition had to decide which mount options to assert,
which meant explaining every option in the live output — and `discard=async`
appears there while no mount command in the build passes it. `btrfs(5)` gives
"(default: async when devices support it since 6.2)". So the *btrfs* half of the
divergence is not a reversal at all: §1.4's deliberate omission stopped meaning
"off" at kernel 6.2 and nobody noticed, because an omission has no diff.

Two layers, two very different histories, found within twenty minutes of each
other by the same mechanism.

## §1.2 refutes itself two sentences apart

The finding that made the ADR worth writing rather than merely recording:

> "this document does not pass `--allow-discards` at format time and does not
> include `rd.luks.options=discard` in the cmdline … SSD wear is managed by
> weekly batch TRIM via `fstrim.timer` instead."

`cryptsetup-open(8)` on `--allow-discards`: "Allow the use of discard (TRIM)
requests for the device." Without the grant, discard requests are not allowed —
and issuing discard requests is the entire job of `fstrim.timer`. **The
configuration §1.2 describes yields no TRIM at all**, on a QLC drive, which is
the opposite of what the paragraph claims to be doing (`inferred`: the option's
semantics are documented, and nobody has run `fstrim` here with the grant
absent).

The two halves of that contradiction are in one paragraph. It survived three
rounds with this document as the primary input, and it was not found by reading
more carefully — it was found by asking whether `luks-format` should pass
`--persistent`, which meant checking the header (`Flags: (no flags)`) and then
asking where the machine's discard grant actually comes from.

The consequence for the record: the privacy argument in §1.2 is untouched — the
`cryptsetup-open(8)` warning about leaking "filesystem type, used space" is still
there verbatim — but the *mitigation* it offers is not an implementable
alternative. Batch and continuous TRIM disclose the same map through the same
grant. The only configuration that honours §1.2's reasoning is no TRIM at any
cadence, which is a position nobody had actually taken.

## The hole I put in my own first draft

`luks-format`'s precondition, as first written:

```
test -b "$LUKSDEV"
! cryptsetup isLuks "$LUKSDEV"
```

Both pass on `sda2`. That is 466 GB of unformatted space on the Samsung T5,
attached during the build, whose other partition is the unencrypted rescue store
of [[../decisions/20260815-t5-rescue-partition-unencrypted|ADR-0009]] — the disk
that exists to be readable when this machine is not. A `luksFormat` aimed there
would succeed, quietly, and the precondition would have approved it.

The defect is not a missing check. It is that **both checks validate the value's
type and neither validates its provenance.** "Is a block device" and "is not
already a container" are true of a great many wrong answers. Tying the parameter
back to what `disk-partition` produced — partition 2 of `$DISK`, by `PARTN` —
narrows it to one.

That generalised into the fourth convention in `_schema.md`: a parameter is named
in prose, guarded with `${VAR:?}` in *every* field that reads it including the
postcondition, and validated against something the DAG established. The middle
clause has its own reason — a postcondition is the half that gets re-run and the
half that gets duplicated into a runbook, so it cannot lean on a guard in the
precondition having run.

**Four of the five conventions in `_schema.md` now come from a specific failure
rather than from foresight** — assert-against-live-state from the PRD's baked-in
UUID and offset, output-parsing-over-exit-codes from `sbctl verify`, don't-fail-
the-same-way-as-what-you-detect from the collector's `"tpm2-pcrs": null`, and now
this one. The fifth, the one-line verdict, is the only one proposed in advance.
That ratio is worth noticing before adding a convention that sounds sensible.

## An edge that is not a data dependency

`btrfs-subvol-mount requires btrfs-default-subvol` looks wrong on first reading.
Mounting consumes nothing `set-default` produces. What it does is *destroy the
condition `set-default` needs*: `set-default` takes an accessible path, `/mnt/@`
exists only while the top level is mounted, and mounting the subvolumes is what
unmounts it.

Without the edge a topological sort can legally order the mount first, and the
build halts at a precondition doing its job. So **"A must happen while B's world
still exists" is as real an ordering as "A consumes B's output"**, and the DAG
has no way to distinguish them — which is fine, because it does not need to.

It has a consequence in the PRD. §1.3 closes with `umount /mnt`, flagged
CRITICAL, and §1.4 mounts the subvolumes. Written that way the default-subvolume
step has nowhere to go: after §1.3 the path is gone, before §1.3 the subvolumes
do not exist. **The unmount belongs to the mount step, not to the creation
step** — one line moved, and the two steps can both run.

## The derived-context rule computes privilege, not namespace

`spec/_index.md` derives a step's execution context from the DAG: chroot-side if
`first-boot` is absent from its transitive closure, booted-system if present. The
corroborating tell it names is `sudo`.

`spec/disk` sits entirely on the near side and shows the limit. Its ten steps run
in the **live installer**, before `pacstrap` and before any chroot exists — and
the rule cannot tell that from chroot-side, because the privilege tell is
identical for both. That would be a harmless imprecision except that **namespace,
not privilege, is what broke the `swapon` precondition** in the first round: the
kernel reported the path recorded at `swapon` time, and which name that is
depends on which side of the chroot you are standing on.

`/mnt/swap/swapfile` and `/swap/swapfile` are one file. Every path in `spec/disk`
carries the prefix and every path in `cmdline-write` does not. The rule answers
"does this need `sudo`" correctly and says nothing about the question that has
already cost a bug. Recorded in `spec/_index.md` rather than fixed, because the
fix is a field and a field is how schema churn starts.

## Three readings of one offset, and why two of them are wrong

The standing invariant for the resume offset needs something to compare the live
`map-swapfile` value against, and there are three candidates. Working the
scenarios out was what settled it:

| Scenario | `/etc/kernel/cmdline` | signed default entry | `/proc/cmdline` |
|---|---|---|---|
| Swapfile recreated, nothing else | FAIL | FAIL | FAIL |
| Recreated, `cmdline-write` re-run, no `mkinitcpio -P` | **PASS** | FAIL | FAIL |
| Fully repaired, not yet rebooted | PASS | PASS | **FAIL** |

`/etc/kernel/cmdline` is intent and passes while four signed UKIs still carry the
old value. `/proc/cmdline` is what booted — and **hibernation is resumed by the
next kernel, not the running one**, so it raises an alarm on a machine that has
just been correctly repaired. Only the signed default entry is right in all
three, and it is right for a reason that took the third row to see: the question
is never "what is true now", it is "what will the next boot find".

The reading itself came with a lookup decision. `bootctl list --json=` would
cover all four UKIs instead of just the default one, but `bootctl(1)` documents
the flag without naming the JSON fields, and guessing field names is how the
`--tpm2-pcrs` class of silent-null bug starts. So the invariant parses
`bootctl status`'s `options:` label, which *is* measured in `state/boot.md`,
accepts the narrower coverage, and names the gap. Channel 5 of the lookup rule,
applied to a parse target rather than to a flag.

## The test for when an invariant is warranted

Two cases now, and together they give a rule that neither gave alone. The btrfs
default subvolume and the resume offset are both properties that are:

1. **established once at build time**,
2. **invalidatable afterwards by a legitimate action** — a rollback, a swapfile
   resized after a RAM upgrade — and
3. **silent when they break.**

A build step whose own postcondition fails loudly satisfies only the first. When
all three hold, the `requires` edge is necessary and not sufficient: it orders
one execution, and the hazard outlives the execution. That is the whole argument
for a command-less step, and it is now stated in `spec/disk` where both examples
sit.

## A measurement that was almost cited as proof

`btrfs(5)` says mount options are filesystem-wide and "only options in the first
mounted subvolume will take effect", which is what makes `compress=zstd:1` on
five of the six mounts inert. The live output looked like an independent
confirmation: `## mounts` shows `/swap` carrying `compress=zstd:1` although §1.4
mounts `@swap` without it.

It is not. `## fstab` carries `compress=zstd:1` on the `/swap` line explicitly,
because `genfstab` copied the options the kernel reported at install time — which
already included it, for the very reason being tested. The reading is circular.
The man page is the source and the live output is consistent with it; it proves
nothing on its own. Caught before it reached the chapter, which is the only
reason it is here rather than in a corrections table.

## Two vault rules collided

The partition type check wants to assert against the type GUIDs, which are
sourced twice from `systemd-gpt-auto-generator(8)`. It cannot: the pre-commit
hook blocks any staged line matching the UUID shape, and `CLAUDE.md` says redact
rather than `--no-verify`. A **standardised type GUID is not an identifier of
anything** — it is the same value on every machine on earth — so it has no
redaction token and the redaction model has no place to put it.

The check therefore greps `sgdisk -i`'s plain type name, and those strings are
`inferred` and marked as such. This is the first case where the hook's bluntness
has a cost beyond an occasional override, and it wants a decision rather than a
workaround: either an allow-list for standard type GUIDs, or a collector section
recording the partition types so the spec can cite `state/` — the second being
cheaper and matching how everything else in the chapter is grounded.

## Conclusions revised

| Claimed | Corrected to | Why |
|---|---|---|
| `test -b` plus `! isLuks` guards the target | Neither says *which* disk | `sda2` on the rescue drive passes both |
| Both TRIM divergences are reversals | The btrfs half was overtaken, not reversed | `btrfs(5)`: async is the default since 6.2 |
| §1.2's stance is the privacy-preserving option | It is the no-TRIM-at-all option | `--allow-discards` gates `fstrim` too |
| The offset invariant reads `/etc/kernel/cmdline` | The signed default entry | Three scenarios; one column right in all |
| `/swap` carrying `compress` proves options are fs-wide | Circular — `genfstab` wrote it there | `## fstab` carries it explicitly |
| The derived-context rule settles execution context | It settles privilege; namespace is separate | `/mnt/swap/swapfile` is `/swap/swapfile` |
| The type GUIDs can be asserted directly | Not committable under the redaction rule | The pre-commit hook blocks the shape |

The first and third are the ones that mattered. Both were cases of a check or an
argument that looked complete because every individual claim in it was true.

## Still open

- `spec/base` and `spec/containers`. Four unresolved ids, recounted rather than
  transcribed this time: `base-install`, `user-create`, `first-boot`,
  `podman-install`.
- The hook-versus-type-GUID collision needs a decision, not a workaround.
- `--pbkdf argon2id` is set by `luks-format` and asserted by nothing, because
  `collect.sh` strips the `PBKDF:` line. One `luksDump` on the machine, or one
  collector change, closes it — and argon2id versus pbkdf2 is the memory-hardness
  of the passphrase, which nothing in `state/` currently records.
- The resume-offset invariant covers the default boot entry only. The fallback
  UKIs are the collector's, not the spec's.
- Stripping `subvol=` from the root fstab line belongs to `spec/base`;
  `btrfs-default-matches-root` is currently the only thing that would notice if
  it were missed.
- Nothing in `spec/disk` has been executed, which is the standing limitation from
  the second round and sharper here: `disk-partition` and `luks-format` are the
  two steps in this vault whose failure mode is destroyed data.
